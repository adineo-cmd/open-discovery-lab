# DiamondWare .dwm Opcode Table Attempt: MID2DWM.EXE EXEPACK Attack (F-47)

**Track:** C — Discovery Engine | **Date:** 2026-11-14 | **Verdict: PARTIAL** (stub RE **completed and independently re-verified instruction-by-instruction**; the F-46 "impossible distance" is **resolved as a forward self-reference into the stream copy** — the packer's LZ dictionary includes its own packed output; full-image recovery still blocked, blocker narrowed to one post-19KB mechanism; opcode table still unpinned)

**Claim.** This session re-attacked the EXEPACK stub of `MID2DWM.EXE` with a from-scratch capstone disassembly and an exact physical-memory simulation. Every branch of F-46's grammar is confirmed byte-exact, and three material corrections/extensions are established: (1) the run copy is a **sliding** copy (`es:[bx+di]` re-evaluated per iteration against `stosb`-incremented DI), not a fixed-offset block copy; (2) the "long-run distance" is **not always a distance** — when `BX+DI` does **not** wrap 16-bit arithmetic, the source address lands **inside the moved copy of the packed stream that the stub keeps in the same segment**, so the decoder reads the packer's own output as dictionary bytes; the F-46 token-37 rejection (w=0x46A1 at DI=42 demanding dist=0x175F) is exactly this case and reads payload[0x6ABB]; (3) the NORM marker is a **physical-address-preserving window slide** whose purpose is to hold DI >= 0x2000 so backward distances up to the 0x2000 (8 KB) window cap never underflow the segment. The stub's DONE path is fully decoded (packed-reloc walker + final far jump). An exact-machine simulation decodes the flag stream cleanly through token 2759 (~19.3 KB image) and then hits a c==0 END — while the entry point demands image offset 0x13600 (79,744 B). Reconciliation of that final contradiction is the single remaining unknown; naive "next section" continuation of the residual 44.5 KB payload is disproven (runs away). The .dwm opcode table therefore remains unpinned; F-41/F-53 envelope and event-type facts stand unchanged.

## Method

1. Re-verified SDK files in `/tmp/dw-sdk` (MID2DWM.EXE 48,923 B, SAMPLE.DWM/SAMPLE.MID, DWS.LIB etc.); corrected MZ parse (`e_cparhdr` at offset 8; load module 48,891 B at 0x20; stub 0x15B bytes at `e_cs*16` = lm+0xBDA0).
2. Full capstone 16-bit disassembly of all 347 stub bytes with hand-verified instruction boundaries (F-46's prose transcription confirmed exactly; DONE path decoded from raw bytes at 0xFC with correct alignment).
3. Exact-machine simulation: physical buffer modeling both payload copies (old copy at [image_base, +0xBDA0) surviving only below 0x7E10 where the move overwrote it; moved copy = entire final stream at [image_base+0x7E10, +0x13BB0)), 16-bit offset arithmetic in `es:[bx+di]` (wraps within the segment), shared SI between flag words and raw bytes, faithful NORM/ES/DS tracking.
4. Cross-validation on the SDK's three sibling EXEPACK binaries (FINDSB.EXE, PLAYDWD.EXE, VOC2DWD.EXE): **same stub** (stub_len=0x15B, entry 0x0E, identical code bytes); their streams open with flag word 0xFFFF followed by clean Borland C0 literals (`55 8B EC B8 xx xx 9A...`) — and **all four** hit the same class of first non-wrapping long token early (DI 16..42), confirming the forward-read mechanism is systematic, not a MID2DWM quirk.

## New finding 1: the copy loop slides with the destination

Stub 0xBB-0xC0: `mov al, es:[bx+di]` / `stosb` / `loop 0xBB`. Because `stosb` increments DI and the source address is recomputed each iteration, each copied byte reads `es:[(BX+DI_k) mod 0x10000]` with DI_k = DI+k — standard LZ77 overlapping-copy semantics (dist < count produces the classic self-referential run pattern). The source offset relative to the destination stays constant at BX (16-bit); both F-46's published decoder and this session's first simulation initially mis-modeled this as a fixed source address.

## New finding 2: the LZ dictionary includes the packed stream itself (the F-46 blocker resolved)

Buffer geometry after the stub's moves (all verified from instructions, not assumed):
- ES:0 = image base (CS_orig - 0xBDA paras). The old payload copy occupies ES:[0, 0xBDA0), but the move overwrote ES:[0x7E10, 0xBDA0) — only ES:[0, 0x7E10) retains the original payload bytes.
- DS:0 = image base + 0x7E1 paras = image_base+0x7E10. The moved copy holds the **entire final packed stream** (payload[0..0xBDA0)) at DS:SI, and it sits **inside the same segment window** the decoder reads via `es:[bx+di]`.
- Therefore: backward references (BX+DI wraps >= 0x10000) read decoded output at DI-(0x10000-BX), dist <= 0x2000 because BX >= 0xE000 always (`or bh,0xE0`). **Forward references (BX+DI does not wrap) read the packed stream at stream offset (DI+BX-0x7E10)** — any byte of the *final* stream, past or future relative to the flag pointer SI, because the whole stream is present from decode start. The packer can literal-encode an image chunk once (those literals live in the stream) and reference the same bytes from any other occurrence via a forward token; BX = stream_off + shift - DI (mod 0x10000) constrained to [0xE000,0xFFFF].

Token 37 (DI=42, w=0x46A1 -> BX=0xE8A1): BX+DI = 0xE8CB does not wrap -> copies 8 bytes from stream offset 0x6ABB into image[42..49]. The F-46 56-variant distance brute force failed because it only tried backward-distance formulas; the correct reading is "backward if wrapped, else forward into the stream copy".

## New finding 3: NORM is a physical-preserving window slide; DONE path fully decoded

- NORM (c==1): DI := 0x2000+(DI&0xF); ES += (DI>>4)-0x200; SI := SI&0xF; DS += SI_old>>4. Both preserve the physical address exactly (verified algebraically and in simulation). Effect: DI is held ~ 0x2000 so all backward distances (<= 0x2000) resolve without segment underflow, and DI never wraps 0x10000 during stosb. First observed NORM fires at DI=0x1A15 (before a run needing dist > 0x1A15), dipping ES 0x5F paras below the image base (window slack, not referenced).
- DONE (c==0 -> CS:0xFC): `push cs/pop ds; mov si,0x158; pop bx (PSP); add bx,0x10 (= image base); mov dx,bx; xor di,di;` packed-reloc walker: `lodsb`; 0 -> `lodsw` (0 = next section: DX += 0xFFF paras; 1 = end; else delta: DI += ax, DI kept mod 16, DX += DI>>4, `add es:[di], bx` fixup); ends with SS:SP from header words [6]/[4], CS word [2] += image base, DS=ES=PSP, `ljmp cs:[0]` to real_cs:real_ip. Reloc table `00 01 00` = zero fixups (e_crlc=0 consistent). Bytes 0xF7-0xFB are padding.
- Entry = image_base + 0x135F*16 + 0x10 = image offset 0x13600 (79,744): the unpacked image must extend to at least 79,744 bytes.

## Simulation result and the remaining single unknown

Exact-machine simulation (sliding copy + forward stream reads + faithful NORMs) on MID2DWM.EXE: tokens 1-36 reproduce the F-46 prefix bit-exactly (Borland overlay-entry stub code: `mov ax,[0x44] / or ax,[0x42] / je +0D / push [0x44] / push [0x42] / push cs / call +0x802 / retf` pattern — overlay stubs, explaining why image offset 0 is not C0 for this binary); the pristine flag stream then runs to token 2759 and terminates at a c==0 END with **19,334 bytes** of output (17,814 physical after the NORM es-dip), having consumed only 4,081 of 48,544 payload bytes. **Contradiction:** entry demands 0x13600. The residual payload [0xFE1, 0xBDA0) is high-entropy; treating it as fresh token sections (walk continuing after each c==0) runs away (22 spurious ENDs, physical 0x318B3, no strings) — disproven. Payload tail inspected at the presumptive entry location (payload[0xB7F0]) is not code. The flag reads are output-independent through the END, so the true decoder's token structure must diverge from pristine-payload flags somewhere after the first ~19 KB — i.e. some buffer/state detail still differs from the model. Leading candidates for next session, in order: (a) the forward-read mapping uses the **old copy** (payload[X] at image_base+X) rather than the moved copy for some address range — i.e. re-derive which physical region serves each (BX+DI) bucket exactly as the packer assumed; (b) the writer/reader race: the output eventually overwrites the moved copy from 0x7E10 up, and the shift (0x7E1 paras) looks engineered so the writer overtakes the reader at a *planned* point — the post-overtake flag words would be read from overwritten memory, implying the stream encodes the remainder differently; (c) a second decompressor pass the DONE path hides (not found in the 347 bytes — all instructions accounted for). Only (a)/(b) affect flag reads.
